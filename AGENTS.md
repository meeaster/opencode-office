# opencode-office

The `office` tool: the CLI (`src/`, run from a checkout by `bin/office`), the built-in packages (`packages/`, among them `office`, which every office runs), the template `office init` copies (`template/`), the base image of the `opencode` container (`image/`) and the compose file for `executor` and `opencode`. `README.md` describes the layout, runtime and commands. Offices are separate repositories, each owning its content (desks, skills, apps, services); that content changes in the office, not here.

- `office` ships as one executable people drop on their PATH, with no Node, npm or checkout beside it. Reach the tool's own files only through `src/tool.ts`, which finds them embedded in the executable or in the checkout; a new folder the CLI reads at run time joins its `assets` list.
- The template is copy-once: `office init` copies it and the office owns the copy, so a template change reaches an existing office only when someone copies it there; when an office you work with should get it too, say so. What every office needs from OpenCode (the guidance, the `office` skill, the `office-executor` MCP server) is the required built-in `office` package, given by its plugin, not the template.
- A package (`package.yaml`, `skills/`, `plugin/`, `scripts/`, `template/`, `gui/`, `compose.yaml`) is a capability an office opts into in `office.yaml`; keep the core to what every office needs to run. It is built-in (this repository's `packages/`, embedded in the executable, listed by name; `office` is required and never listed), remote (another repository's, by `repo`, `path` and `ref`) or local (the office's own `packages/<name>/`); `src/packages.ts` resolves the kind. Built-in and remote packages are pulled into the office's `.office/packages/<name>/` and are read-only there: `office check` reports an edit and `office sync` restores the copy. A built-in package follows the executable, so a change here reaches an office when it runs `office sync` with a new `office`; commit what sync writes there. `src/build.ts` stages the built-in packages as offices get them in `target/packages/`, which the executable embeds as `packages/`; `builtinFiles` in `src/tool.ts` gives the same files run from a checkout. `src/migrate.ts` moves an office from an earlier release's layout; keep each step idempotent. Package scripts run with nothing but Bun, in the office and in its CI, so a library a script needs is committed in the package as a self-contained file, regenerated from an exactly pinned devDependency by a repository script (artifact-share's `scripts/vendor/`, `pnpm run vendor-artifact-share`); a package plugin, linked as `.opencode/plugins/<name>`, imports only what OpenCode's runtime provides, or ships its own bundle, as `office` does: its plugin imports the CLI's schema, so `bundlePlugin` in `src/tool.ts` builds it into the one `plugin/index.js` an office holds (`bundledPlugins`). OpenCode resolves a plugin's relative imports from the link, so a plugin reads files outside `plugin/` (its skills, `.settings.json`) through `realpathSync`, never by importing them. A package reaches OpenCode only through its own plugin: the plugin registers the package's skills (`ctx.skill.transform`) and MCP servers (`ctx.mcp.transform`) along with its tools and hooks. `office sync` links nothing else of a package into `.opencode/`, `package.yaml` declares nothing OpenCode loads, and no plugin loads another.
- A package may have a desktop app panel: `gui/` with its source, its build dependencies and the committed bundle `gui/dist/gui-experimental.cjs`, discovered by that file. The app loads panels only from its own sidecar, which reads the config of the machine the app runs on, so `office sync` copies the bundle there (`src/desktop.ts`: the host, or Windows from WSL; nothing from inside the container) with a generated GUI-only `package.json` named `office-<name>`, and adds the folder to `plugins` in that machine's `opencode.json`, editing only that list. The panel reads data over RPC from the package's plugin on the session's server. The install is per machine and the last sync wins; panels are never removed automatically. Tests and scratch runs set `OFFICE_APP_CONFIG_DIR` and `OFFICE_APP_PANELS_DIR`, so they never touch the real config.
- A package's root `compose.yaml` adds services to the office's compose project (`src/package-services.ts`). `office up` runs a copy of it kept in the state folder, applied like the pins (new on a plain `up`, a change only with `--upgrade`), through a generated include that gives it the package's folder for relative paths and its own settings and secrets for interpolation; its services, volumes and variables are named after the package's namespace (`namespace:` in `package.yaml`, else its name), while its state stays keyed by the package name; every compose command takes the same files from `composeArguments`.
- A package's `tools:` in `package.yaml` names mise tools at exact starting versions (`src/package-tools.ts`). `office sync` writes them into the office's own `.mise/conf.d/<name>.toml`, which the office commits and owns: sync adds and removes tools as the package declares them but never changes a version, `office upgrade-tools`, the container's entrypoint and host mode's `office up` treat the fragments like the office's `mise.toml`, and the office's `mise.toml` wins over them. A built-in package's starting version respects the same three-day minimum age as packages.
- A host-mode office manages its machine (`src/machine.ts`): what it writes outside its folder and state is whole files named `office-<name>-…`, listed in the machine record (`$XDG_DATA_HOME/office/machine.json`) that also names the one office managing the machine, written only after the user's yes in `office setup` (`--manage-machine`), removed with their fragment or package, when the office leaves host mode, or by `office sync --release-machine`, left by `office down`, and checked by `office check`. Never edit a file the office didn't write or replace a path the record doesn't list. The first such files are links from mise's global conf.d to each file in the office's `.mise/conf.d/` (`machine.toml`, the office's own, linked last so it wins; `machine` is a reserved package name); the container links them inside itself at start. A hook or task in a fragment finds the office from `config_source`, never a relative path, since mise runs a linked file's from the home folder. Tests and scratch runs set `OFFICE_MACHINE_RECORD` and `OFFICE_MISE_CONFIG_DIR` (`bun test` does through `bunfig.toml`); never set `MISE_GLOBAL_CONFIG_FILE` for anything agents or the office's tools run under, as it switches global conf.d off (the private host-tools mise in `src/host-tools.ts` is separate).
- `opencode:` in `office.yaml` decides what agents have. Host mode: OpenCode runs on the machine itself and has what it has, the user's desktop Chrome through Browse included. Container mode: no desktop; agent-browser, and the in-app browser when the desktop app is attached. Services are containers in both. Packages learn the mode as declared, from `.office.json` that sync writes beside `.settings.json` (`{ "opencode": "host" | "container" }`), never by detecting their environment (`OFFICE_CONTAINER` is for addresses only). A package's `host:` block in `package.yaml` (tools, and an `install` of a file outside the office, run as its fragment's `postinstall` hook and `<package>:install` task) applies only in host mode; everything after the fragment's `[tools]` table is sync's.
- Browse is the one thing an office installs and never pins: the browser package installs it once and it updates itself, as its Chrome extension does. Keep it that way: the relay and extension negotiate a protocol, so a pinned relay drifts out of compatibility with the self-updating extension, and Browse releases too often to pass a minimum age.
- `packages/office/plugin/instructions.ts` is the one source of the guidance the `office` package's plugin injects; `office instructions` runs the same file, bundled into the executable.
- `src/schema.ts` is the one shape of `office.yaml`, used by the CLI and bundled into the `office` package's plugin. Read external data (YAML, JSON, API answers) through `check(v.safeParse(schema, data))` at the boundary and pass typed values inward.
- The CLI is TypeScript on Bun (Bun APIs are fine; it never runs on Node), with pnpm for packages. Runtime dependencies are `yaml` (reading and editing YAML with its comments) and `valibot` (schemas); add another only when the user agrees, exactly pinned, and remember it is bundled into the `office` package's plugin if the plugin imports it. Check with `pnpm run typecheck` and `pnpm test`.
- Agents are deliberately unrestricted; the container is the boundary (in host mode, the host server's own configuration is). Add permission rules only when the user asks.
- Only OpenCode has a mode (`opencode:` in `office.yaml`): its container, or a server already running on the host that the office never starts or stops. Executor and an office's own services always run in containers. Take OpenCode's address and the session folder from `office.opencode` (`src/office.ts`); Executor apps get them from `office.ts`, which `office apps deploy` generates per mode.
- The office has one Executor key (`office-executor.env` in its state), which the `opencode` container and the office's own services share; every other service credential lives in Executor.
- Keep every published port on `127.0.0.1`.
- Each office pins OpenCode, Claude Code, Executor and mise in its own `office.yaml`, with checksums in `office.lock`; the tool holds only the versions a new office starts at and the range it was tested with (`defaultPins` and `tested` in `src/versions.ts`), so raise those together after testing. The tool pins the rest exactly: supercronic and the Debian base by SHA-256 and digest in `image/Dockerfile`; Bun, pnpm and pre-commit in `mise.toml`. Never let an office run an older OpenCode or Executor than it has run: their data migrates forward only. Packages must be at least three days old (`pnpm-workspace.yaml`), tools at least a day. Browse is the one exception, installed unpinned (above).
- Cron job scripts in an office stay plain shell that knows nothing of the runner. Container mode wraps them for supercronic with stamps and catch-up (`src/cron/container.ts`); host mode generates systemd user timers with `Persistent=true` (`src/cron/host.ts`).
- Release lookups: for `mise.toml` tools, the cutoff comes from mise itself (`mise latest --minimum-release-age <age>`); for the four versions in `office.yaml`, from each project's GitHub release list, filtered to the line the office runs (`sources` in `src/releases.ts`), without a login.
- Executor app sources in the template must type-check against the `apps` version Executor reports; `office apps deploy` checks every app that way before deploying and sets its `apps` dependency.
- This repository is public: commit nothing personal or machine-specific (home paths, emails, IDs, credentials). The gitleaks pre-commit hook (`pre-commit install`) and the workflow's gitleaks job catch secrets.
- Every push to `main` publishes a pre-release through `.github/workflows/release.yml`, built with `pnpm run build --prerelease <UTC datetime>`. `office update` (`src/commands/update.ts`) installs from those releases, so keep its tag pattern, the `office-<platform>-<arch>` asset, `SHA256SUMS` and the release's target commit in step with the workflow. In workflows, pin each action to a full commit SHA with its version in a comment, keep `permissions` minimal per job, and check changes with `actionlint` and `zizmor --min-severity high`.
- Verify a change with `pnpm run install-office`, then `office init` in a scratch folder outside this repository followed by `office check`, and `office check` in an office that is running (it compares the host's and the container's `office --version`; rebuild that office's image with `office up` after changing `image/` or the CLI). Prove host-mode changes in a scratch office against a host OpenCode server, on other ports (`EXECUTOR_PORT=42440`) with `state:` inside the scratch folder, so they never touch a running office.
