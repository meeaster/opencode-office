# opencode-office

## Design decisions

- Prefer deep modules with narrow interfaces: when several callers need the same internal rule, give one module ownership and expose only what callers need to decide or do.
- Before design or architecture work, read [VISION.md](VISION.md): what the project is for and where it is going.
- **Stage: exploration.** The project is still working out its architecture, features and API. Scope each design and slice to the main path: prove the architecture and deliver something that works and is useful. Give failures one plain rule, stop and name what broke. Park hardening (recovery from partial failure, rare edge cases, concurrent runs, version skew, migration) as a named later item, and say in the proposal what was parked. This sets scope and order, not quality: what is built is still well designed and tested.
- The CLI holds no migration or compatibility code: an office, machine or container in a state an earlier release wrote gets the ordinary error (unknown key, conflict, missing file) or is left as it is. A migration that is needed is a script run outside the CLI.
- A brainstorm is a design session: explain the user-visible tradeoff and recommend an option. Wait for the user to choose before building; delegation needs approval for that piece of work.
- Build office-specific integrations in the consuming office. Offices can share packages without making them built-ins. The required `office` package owns workspace guidance and OpenCode tooling; other capabilities are opt-in. An office need not have working repositories or Executor apps.
- `template/` is copied once. Put guidance every office should receive on update in the required package’s plugin; put owner-selected settings in `office.yaml`. If an existing office needs a template change, call out the adoption step.
- Only OpenCode has a host/container mode. Host mode uses an existing server that `office` never starts or stops; container mode adds a server without precluding work from the host. Executor and office services run in containers in either mode. Agents are deliberately unrestricted: the container or the host server's own configuration supplies the boundary. Add agent permission rules only on request.
- Bind published ports to loopback. The office's services share its Executor key; keep other service credentials in Executor. This is a public repository: use portable examples without personal paths, identities or credentials.

## Documentation

- `docs/` describes the tool as it is now, for someone learning it: how to use it and its features, and how it is built. Update a doc in the same change as the behavior it describes. The same holds for every `AGENTS.md` (root, `src/`, `packages/`, `.github/workflows/`): when a change makes a line stale, fix or remove it in that change. Designs, plans, handoffs and research live outside the repository; carry a lasting rule they produce into the nearest `AGENTS.md`, as `src/AGENTS.md` does for terminal rendering.

## Verification and adoption

- Set the fixture home, state directories, executable search path and service endpoints **before starting the test runtime**. Runtimes can cache paths at startup; a preload that changes the environment later may leave the runner or its children using the developer's machine.
- Write and clean up only resources the fixture created. When testing discovery through PATH, config or symlinks, create the expected target first and compare discovery against it. Test isolation with a disposable parent containing a misleading shim or config; verify its files stay unchanged after the child exits.
- For intermittent failures, identify the resource the operations actually share. Reproduce the overlap deliberately (two worktrees can share one Git ref store), and verify independent resources can still run in parallel rather than retrying or serializing the suite.
- Tests come in two groups. End-to-end tests (`*.e2e.test.ts`) spawn the compiled office; every other test is a unit test, including ones that use temporary folders and real Git. Check a function with a unit test, and keep end-to-end tests for behavior only the executable shows.
- Unit tests are the fast group and end-to-end tests the slow one: run the unit tests often and the end-to-end tests rarely. While working, run the files you touched (`./bin/test ./src/machine.test.ts`, `./bin/test ./packages/browser/test`, **from the repo root** so `bunfig.toml` preloads the machine-isolation fixture) and `pnpm test`, the unit tests. Run `pnpm test:e2e` when a change reaches the executable's behavior, and `pnpm run typecheck` and `pnpm test:all` once before committing. Release CI typechecks and builds but does not run tests. Launcher tests need host `jq`.
- Keep both groups fast. Bun runs files in parallel, so a file is the unit of wall time: split an end-to-end file by theme before it passes about 20s, with its files sharing a fixture module (`src/package-definition.fixture.ts`, `src/opencode-scope.fixture.ts`). A unit test takes Bun's default timeout; don't raise it, and move a test that needs longer to the end-to-end group.
- Every test earns its place: it guards behavior someone relies on and fails when that behavior breaks. When a change touches code, review the tests around it in the same change: merge tests that overlap, delete tests that duplicate another or only pin implementation details, and speed up slow ones. Report `pnpm test` and `pnpm test:all` times before and after a change that moves them.
- `bin/office` runs checkout sources; it cannot prove assets made it into the executable. For runtime changes, `pnpm run install-office`, then `office init` and `office check` in a scratch folder outside the repo. In a running container-mode office, rebuild with `office up` after CLI or image changes, then `office check` to compare host and container versions.
- For manual host-mode checks, use a host OpenCode server and a scratch office with its own `name:` (it names the office's Compose project, systemd units and images), scratch `state:` and separate ports (the OpenCode `url:` in its `office.yaml`, and `EXECUTOR_PORT`). Redirect `OFFICE_MACHINE_RECORD`, `OFFICE_MISE_CONFIG_DIR` **and** `OFFICE_MACHINE_DIR` into scratch; panel installs also need `OFFICE_APP_CONFIG_DIR` and `OFFICE_APP_PANELS_DIR`. Start that server with scratch `XDG_*` dirs and a disposable `OPENCODE_SERVER_PASSWORD`, saved as `OPENCODE_PASSWORD` in the scratch `state:`'s `secrets.env`. When done, run `office down` in the scratch office with the same variables, stop the server, remove its `office-<name>_*` volumes and its entry in mise's `trusted-configs`, then delete its folder. The Bun test preload does not protect manual runs.
- A built-in package change reaches an office through a new executable and `office sync`; commit the synced files in that office when adoption is requested. Edit package sources, not the read-only copies under `.office/packages/`.
