# Create an office package

Build in the office that needs the capability. Local sources live under `packages/<name>/` beside `office.yaml`; `.office/packages/` holds installed copies that sync restores. Choose a name distinct from a built-in and from the reserved names `machine`, `mise`, `config` and `sdk`.

## A package that teaches a skill

For example, an office that wants agents to prepare release notes could select a package called `releases`:

```text
packages/releases/
  package.json
  office.ts
  skills/draft-release-notes/SKILL.md
  plugin/index.ts
```

1. Write `package.json` with `{ "name": "@office/releases", "description": "Draft release notes from merged changes", "private": true, "exports": {}, "office": { "definition": "./office.ts", "dependencies": ["@office/opencode"] } }`, then `office.ts` with `import { opencode } from "@office/opencode"; import { Package } from "@office/sdk"; export default Package.define({ setup(ctx) { opencode.plugins.add(ctx, { directory: "plugin" }); } });`: OpenCode loads only a plugin folder the package registers, never one found by its name. The name and description live only in `package.json`. Office loads the file `office.definition` names (a module made with `Package.define`, or a `package.yaml`), including during `check`; use relative imports for private modules. `@office/sdk` is always available: never list it in `office.dependencies`. To share a module, list it in `exports` (`"./contract": "./contract.ts"`); consumers import `@office/releases/contract` at module scope and list `"@office/releases"` in their own `office.dependencies`, type-only imports included. A definition imports only `@office/…` packages, Node's built-ins and its own files. The package name is what the office selects; `draft-release-notes` is what the agent invokes.
2. Write the skill with `name: draft-release-notes`, a one-line `description` saying when to use it, and the instructions. Follow the `opencode-plugin` skill's asset lookup and registration guidance: add the ID, name, description, absolute `SKILL.md` path and body through `ctx.skill.transform`.
3. Append `- name: releases` to `packages:` in `office.yaml` and run `office sync` from the office. Sync delivers the registered plugin for every session in the office without an OpenCode config entry. To offer a standalone skill the office enables by ID, register it with `skills.add(ctx, { directory })` from `@office/skills`.
4. Run `office check`, then use the capability from a fresh session in the office: load `draft-release-notes` and try it on a merged change. A file on disk proves neither registration nor usable instructions. If the runtime is unavailable, report which part you actually verified.

## Choose files by who owns them

- **The package maintains it:** keep instructions, reference files and scripts inside the package. Ship scripts ready to run; sync doesn't install their dependencies.
- **The package adds an `office` command:** import its handler in its definition and declare it under `commands`: `commands: { "releases show": { summary, usage: "<tag>", result } }`, with optional `aliases` and exactly one handler. Use `result` when the command's output is data (a list, text another program reads): it returns the text, which becomes all of standard output only when the command succeeds; print progress and diagnostics, Clack included, to standard error. Use `run` when it acts: runs a script, prompts or streams, with the caller's terminal and exit status. The handler receives `{ office, entries, settings, args }`: `office` (its `dir`, `name`, `mode` and `launcher`), `entries` to read a registry, the package's settings as `office.yaml` has them now, `args`, the words typed after the name exactly as given (flags and paths with spaces included), and `executor`, an authenticated request to the office's Executor plus an OpenCode account link, absent when the runtime has none; parse the args yourself, and fail on words a command doesn't take. Put the work inside the handler. A package with only `commands` needs no `setup`. After `office sync --packages`, verify the route in `office --help` and invoke it. Each run loads the packages as they are, so edits to the handler, settings, names and aliases show without a sync; sync still validates and applies them. A name whose first word is one of the CLI's own commands is reserved; the longest declared name wins, so `releases` and `releases show` can both exist. The installed `references/office.ts` is a working example.
- **The package supplies a reference checkout:** import `repositories` from `@office/references/repositories` at module scope and declare `@office/references`. Call `ctx.add(repositories, { name, url, ref, description })`; `ref` and `description` are optional. Gate it on a boolean setting (`source_reference: { type: "boolean", default: true, description: "Include the source checkout" }`, read as `ctx.settings.source_reference`) if the owner may already declare the same name. Verify `office sync --packages`, `office references list`, then `office sync --references`. The installed `references` package shows how to define a registry with `Registry.define({ id: "<package>.<name>", key: entry => entry.name, parse })`, register it with `ctx.registry(handle)` and read it in a command, each entry with its `owner` and `folder`. An entry is any JSON object, with no required `name`: `parse` checks the fields it needs. `key` makes entries unique (two with one key fail the run, naming both owners); `keyScope: "package"` keeps keys unique only within each adding package; without `key`, equal entries are all kept.
- **The office customizes it:** declare a starter file (a seed) in `setup` with `seeds.add(ctx, { destination, source })` (a file or folder in the package, any name) or `{ destination, text }`, importing `seeds` from `@office/seeds` and listing `"@office/seeds"` in `office.dependencies`. `destination` is office-relative, never under `.office/`, and may come from a setting. Sync seeds it once; later syncs preserve the office's edits and deletions, replace an unchanged file when the seed changes, and offer the change to an edited one (`office seeds diff`). A bad declaration (a missing source, two packages on one path) stops every seed in that sync, naming the package; dropping a seed or deselecting the package leaves its files. For this feature, exercise a second sync after editing the seeded file.
- **The office configures it:** declare `settings` as one JSON Schema with `type: "object"` at its root, usually `additionalProperties: false`, each property with a `type`, a `description` and a `default`, or listed under `required`. `ctx.settings` is typed from it. Every package's settings are checked, with defaults applied, before any `setup` runs; values are checked against their type (`"4600"` isn't an integer). The office supplies overrides on its package entry; the plugin reads resolved values, booleans included, from its entry of the office's applied settings inside its hook or transform (`@office/sdk/applied-settings`, bundled into the plugin; a shell script runs `office settings get <package> --office <root>`), and top-level text, numbers and booleans reach a `compose.yaml` as `<NAMESPACE>_<NAME>`. A setting gating a system setup must be a boolean with `default: false`.
- **The package uses another only when the office selects it:** don't list it in `office.dependencies` or import it from the definition. Map it in `package.json` as `"office": { "integrations": { "@office/skills": "./skills.ts" } }`; `skills.ts` imports the provider and default-exports `Package.integration<typeof definition>()({ setup(ctx) { if (ctx.settings.skills !== false) skills.add(ctx, { directory: "skills/review" }); } })`, with `import type definition from "./office.ts"`, so `ctx.settings` is the package's own. Office runs it whenever the provider is selected, so it adds only what the settings ask for. In the base definition's `setup`, reject an explicit request for an unselected provider, naming it: `if (ctx.settings.skills === true && !ctx.providers.selected("skills")) throw new Error("skills: true needs package skills, …")`; never fall back to another route silently. Keep every option in the package's one settings schema; give a switch whose omission must differ from `false` no `default`, and put cross-field rules in the schema. Verify in a scratch office alone, with the provider selected and the settings adding nothing, adding, and explicitly requesting it with the provider removed again, before and after `office sync`.
- **The package offers an Executor app:** keep the app's source in a folder of the package, such as `executor-app/` with its `package.json`, `index.ts` and a `package.ts` holding the settings' defaults, and offer it from an adapter for `@office/executor` (mapped under `office.integrations`, as above): `apps.add(ctx, { directory: "executor-app" })` from `@office/executor/apps`. The app deploys under the package's namespace with a `package.ts` generated from the office's settings; never deploy it from the package itself. The installed `design` package's `executor.ts` is the example. Verify with `office apps deploy` against a scratch office's Executor.
- **The package schedules a script:** import `cron` from `@office/cron`, list `"@office/cron"` in `office.dependencies`, and in `setup` call `cron.add(ctx, { name: "digest", schedule: "@daily", script: "scripts/digest.sh" })`; ship a regular package-relative `.sh` file in plain shell and put the work there. Add `when: "host"` (a managed host too), `"managed-host"` or `"container"` for a job that runs in one mode only; it stays declared elsewhere, so an office's override for it stays valid. For a job a setting turns on, don't add it while the setting is off. The office overrides a job by its id, `package.<package>.<name>`, under the cron package's `settings.overrides`. For work at each sync, declare a `sync({ office, entries, settings })` function on the definition instead: it runs after every `setup`, once every selected package loaded, and returns lines to print; a `check` function returns `{ level, message }` problems for `office check` and must write nothing; `up` and `down` run at `office up` and `office down` (`down` gets no `entries`) and can set the package's own systemd timers through `host.timers`. Use the installed `office/office.ts` as an example. Verify the id with `office cron list`, then run it with `office cron run <id>` in a scratch office.
- **The package needs a CLI:** write `import { tools } from "@office/tools"` (declare `@office/tools`) and, in `setup(ctx)`, call `tools.require(ctx, { name: "npm:agent-browser", minimum: "0.43.0", bin: "agent-browser" })`: a mise registry short name or a backend-qualified name, the exact version the package was tested with, and every executable it exposes. Add `hostOnly: true` for a host tool; require it inside an `if` on a setting when only that feature needs it. Packages requiring one tool share one release, at least every minimum; `office bump` records it in `office.lock`, `office up` installs it, and an exact `machine.toml` pin holds it. A tool the package stages itself is `tools.provide` with a task in its own `mise.toml`.
- **The package exports a mise task:** import `tasks` from `@office/mise-integration/claims` (declare `@office/mise-integration`); `ctx.add(tasks, { name: "audit", description: "Audit the workspace", script: "scripts/audit.sh" })` gives `mise run <package>:audit`. Run it outside the scratch office through its machine link. No tool claim is needed.
- **The package installs something once on the host:** add to `installs` from the same contract. `destination` owns the installation; `ready` names the executable or regular-file marker (`executable: false`). Setup registers the package-relative script; the postinstall hook runs it only when missing. For a default-off system bootstrap, see `browser/office.ts`. Supported native sections are `bootstrap.packages`, `bootstrap.files` and `bootstrap.directories`. Each path has one owner; present directories may contain managed children. Unconditional present files also supply readiness checks; absent, OS-filtered and `remove_empty` targets do not. List additional positive checks in `ready`. Different specs for one native package conflict; side effects of scripts are not inferred. Only `office setup` offers application.
- **The package runs a long-lived host process:** in a host-mode office, select the official `systemd` package, list `"@office/systemd"` in `office.dependencies`, and in `setup` call `systemd.userUnits.add(ctx, { id: "greeter", file: "units/greeter.service" })` for a unit file the package ships, or `render: facts => text` to build it at `office up` (`facts.launch(script)` gives a package script's `Environment=`/`ExecStart=` lines, `facts.executable(handle)` a stable path to an applied tool). Name what the process depends on in `restartWhenChanged` (a `tools.require` handle, package files such as a bundle): a change restarts it on `office up --upgrade` without rewriting the unit. Add `ready: ({ pid, facts }) => …` when systemd's active state isn't enough, such as a local authenticated request. Plain `up` holds a running unit with pending changes; office refuses a unit file it didn't write, and `Also=` or `Alias=` in the unit's text. Verify the unit's bytes, `office up` twice (no restart), `office check`, and `office down`, against a scratch office.
- **The package's services create Docker resources themselves** (a service with the Docker socket mounted starts containers, networks or volumes outside the compose project): have them label what they create and declare it as `spawns: { label: <key>=<value> }`, the value naming `${OFFICE_NAME}` once and the package's namespace, such as `floci_namespace=office-${OFFICE_NAME}-floci`. `office down` then removes the labelled containers and networks and keeps the volumes; the installed `aws-emulator` package shows the shape.
- **The package adds a desktop panel:** use `opencode-plugin` for `gui/`, the committed bundle, and verification in the desktop app.

To share the result, keep the same package layout in a repository. Another office selects it with `name`, `repo`, `path` and `ref` under `packages:`; pin a tag or full commit SHA and sync there.
