# Create an office package

Build in the office that needs the capability. Local sources live under `packages/<name>/` beside `office.yaml`; `.office/packages/` holds installed copies that sync restores. Choose a name distinct from a built-in and from the reserved names `machine`, `mise`, `config` and `sdk`.

## A package that teaches a desk skill

For example, an office that wants agents to prepare release notes could select a package called `releases`:

```text
packages/releases/
  package.json
  office.ts
  skills/draft-release-notes/SKILL.md
  plugin/index.ts
```

1. Write `package.json` with `{ "name": "@office/releases", "description": "Draft release notes from merged changes", "private": true, "exports": {}, "office": { "definition": "./office.ts" } }`, then `office.ts` with `import { Package } from "@office/sdk"; export default Package.define({});`. The name and description live only in `package.json`. Office loads the file `office.definition` names (a module made with `Package.define`, or a `package.yaml`), including during `check`; use relative imports for private modules. `@office/sdk` is always available: never list it in `office.dependencies`. To share a module, list it in `exports` (`"./contract": "./contract.ts"`); consumers import `@office/releases/contract` at module scope and list `"@office/releases"` in their own `office.dependencies`, type-only imports included. A definition imports only `@office/…` packages, Node's built-ins and its own files. The package name is what the office selects; `draft-release-notes` is what the agent invokes.
2. Write the skill with `name: draft-release-notes`, a one-line `description` saying when to use it, and the instructions. Use the `opencode-plugin` skill to implement its registration: from `setup(ctx)`, register a `ctx.skill.transform` that reads the skill and adds its ID, name, description, absolute `SKILL.md` path and body. Resolve the package directory from the **real** plugin directory because OpenCode loads it through a symlink. This makes references beside `SKILL.md` work from any desk.
3. Append `- name: releases` to `packages:` in `office.yaml` and run `office sync` from the office. Sync links the plugin for all desks; no `skills.enabled` or OpenCode config entry is needed.
4. Run `office check`, then use the capability from a fresh desk session: load `draft-release-notes` and try it on a merged change. A file on disk proves neither registration nor usable instructions. If the runtime is unavailable, report which part you actually verified.

## Choose files by who owns them

- **The package maintains it:** keep instructions, reference files and scripts inside the package. Ship scripts ready to run; sync doesn't install their dependencies.
- **The package adds an `office` command:** import its handler in its definition and declare it under `commands`: `commands: { "releases list": { summary, run } }`, with optional `aliases`. `run` receives `{ read, settings }`, the package's settings as `office.yaml` has them now; put the action inside `run`. A package with only `commands` needs no `setup`. After `office sync --packages`, verify the route in `office --help` and invoke it. Each run loads the packages as they are, so edits to the handler, settings, names and aliases show without a sync; sync still validates and applies them. A name whose first word is a built-in command is reserved. The installed `references/office.ts` is a working example.
- **The package supplies a reference checkout:** import `repositories` from `@office/references/repositories` at module scope and declare `@office/references`. Call `ctx.add(repositories, { name, url, ref, description })`; `ref` and `description` are optional. Gate it on a boolean setting (`source_reference: { type: "boolean", default: true, description: "Include the source checkout" }`, read as `ctx.settings.source_reference`) if the owner may already declare the same name. Verify `office sync --packages`, `office references list`, then `office sync --references`. The installed `references` package shows how to define a registry with `Registry.define({ id: "<package>.<name>", parse })`, register it with `ctx.registry(handle)` and read it in a command, each entry with its `owner` and `folder`.
- **The office customizes it:** put a starter file (a seed) under `seed/` at its intended office-relative path, never under `.office/`. Sync seeds it once; later syncs preserve the office's edits and deletions, replace an unchanged file when the seed changes, and offer the change to an edited one (`office seeds diff`). For this feature, exercise a second sync after editing the seeded file.
- **The office configures it:** declare `settings` as one JSON Schema with `type: "object"` at its root, usually `additionalProperties: false`, each property with a `type`, a `description` and a `default`, or listed under `required`. `ctx.settings` is typed from it. Every package's settings are checked, with defaults applied, before any `setup` runs; values are checked against their type (`"4600"` isn't an integer). The office supplies overrides on its package entry; the plugin reads resolved values, booleans included, from the package's `.settings.json` inside its hook or transform, and top-level text, numbers and booleans reach a `compose.yaml` as `<NAMESPACE>_<NAME>`. A setting gating a system setup must be a boolean with `default: false`.
- **The package schedules a script:** add `registerCron(ctx: CronContext)` to the definition. Import `CronContext` from `@office/sdk`; it is transitional, until cron is a registry. Call `ctx.cron.job("digest", { schedule: "@daily", script: "scripts/digest.sh" })`; ship a regular package-relative `.sh` file. Return synchronously and put the work in the script. For a conditional job, omit the call when no override needs that name, or pass `false` instead of the definition to keep an override valid in other modes. The hook sees current `ctx.settings` and `ctx.cron.mode`; `setup` registers and adds to registries, and commands are declared under `commands`. Use the installed `office/office.ts` as an example. Verify the qualified ID with `office cron list`, then run it in a scratch office.
- **The package needs a CLI:** write `import { requirements } from "@office/tooling/requirements"` (declare `@office/tooling`) and, in `setup(ctx)`, call `ctx.add(requirements, { name: "npm:agent-browser", minimumVersion: "0.43.0" })`. Add `hostOnly: true` for a host tool. Multiple packages may need a tool; sync adopts the highest floor unless the adopted pin is already newer. `machine.toml` overrides it. Check the pins and claimants in `machine.packages.toml`.
- **The package exports a mise task:** import `tasks` from `@office/mise-integration/claims` (declare `@office/mise-integration`); `ctx.add(tasks, { name: "audit", description: "Audit the workspace", script: "scripts/audit.sh" })` gives `mise run <package>:audit`. Run it outside the scratch office through its machine link. No tool claim is needed.
- **The package installs something once on the host:** add to `installs` from the same contract. `destination` owns the installation; `ready` names the executable or regular-file marker (`executable: false`). Setup registers the package-relative script; the postinstall hook runs it only when missing. For a default-off system bootstrap, see `browser/office.ts`. Supported native sections are `bootstrap.packages`, `bootstrap.files` and `bootstrap.directories`. Each path has one owner; present directories may contain managed children. Unconditional present files also supply readiness checks; absent, OS-filtered and `remove_empty` targets do not. List additional positive checks in `ready`. Different specs for one native package conflict; side effects of scripts are not inferred. Only `office setup` offers application.
- **The package needs an Executor app:** put it in `executor-app/` and declare `executor_app` in the package definition, optionally gated on a boolean setting. `office apps deploy` deploys it under the package's namespace with a generated `package.ts` of resolved settings; the installed `design` package's `executor-app/` and README show the shape.
- **The package's services create Docker resources themselves** (a service with the Docker socket mounted starts containers, networks or volumes outside the compose project): have them label what they create and declare it as `spawns: { label: <key>=<value> }`, the value naming `${OFFICE_NAME}` once and the package's namespace, such as `floci_namespace=office-${OFFICE_NAME}-floci`. `office down` then removes the labelled containers and networks and keeps the volumes; the installed `aws-emulator` package shows the shape.
- **The package adds a desktop panel:** use `opencode-plugin` for `gui/`, the committed bundle, and verification in the desktop app.

To share the result, keep the same package layout in a repository. Another office selects it with `name`, `repo`, `path` and `ref` under `packages:`; pin a tag or full commit SHA and sync there.
