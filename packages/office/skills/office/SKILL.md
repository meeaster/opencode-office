# Working on the office

Use `office` from any folder inside the office; `office.yaml` declares its structure. For onboarding after init/clone, run `office setup`. Credential display is human-only: let the human run `office executor credentials` in their terminal, keeping passwords out of agent transcripts. Private age identities and runtime state belong outside the repo; commit only public recipients and SOPS-encrypted records.

| To | Do |
|---|---|
| Add a working repository | With the `repos` package selected, add `{ name, description, url?, ref? }` under its `settings.entries`, then `office sync`: it clones one with a `url` into `repos/<name>/` (at `ref` the first time) and later only fetches it, never changing its branch or files; one without a `url` is listed for sessions and its checkout is the owner's to create. Removing an entry leaves the checkout. Throwaway work and worktrees go in `scratch/`. Both stay out of the office's commits |
| Add a reference | Add `{ name, url, ref?, description }` under `references:`, then `office sync` |
| Add a skill | With the `skills` package selected: create `skills/<id>/SKILL.md`, list `{ folder: skills }` under its `settings.sources` and the ID under `settings.enabled`, then `office sync` to link it as `.agents/skills/<id>`, which every session in the office, inside working repositories too, gets. A skill folder of your own placed in `.agents/skills/` directly also loads everywhere, untouched by sync. `office skills list` shows what the sources offer and what is enabled |
| Use skills from another repository | Add `{ repo, ref, track?, skills: [{ name, path }] }` under the `skills` package's `settings.sources` (`ref` a full commit SHA), enable each ID under `settings.enabled`, then `office sync`: it fetches that commit once into `.office/skills/git/` and links each enabled folder. Nothing of it is committed |
| Update Git skill sources or remote packages | Give the source or package a `track`: a branch, or a tag pattern such as `v2.*` (highest stable SemVer wins). `office skills update` or `office packages update` records the resolved full SHA as `ref` and applies it, each touching only its own pins; `office packages update` also moves the `office.lock` commit of an untracked package whose `ref` is a tag or branch, leaving `office.yaml`. A source or package that can't move (no match, missing skill) keeps its pin. `office sync` applies pins but never moves them; `office refresh` runs both updates. Commit `office.yaml` and `office.lock` |
| Add a plugin | A local plugin goes in `.opencode/plugins/<name>/`, a real folder that is the office's own: commit it, and sync never touches it. Links there whose target is a package's plugin or `../../.office/plugins/<name>` are `office sync`'s: it manages them and keeps them out of Git, and it refuses to replace an entry of the office's own with the same name. A published plugin is one line in `.opencode/opencode.jsonc` `plugins`. One developed in another repository goes under `plugins:` in `office.yaml`: sync clones it into `.office/plugins/<name>` and links it. When sync says to restart OpenCode to pick up a plugin, its location changed and a running server keeps the old one until restarted |
| Add a package | An official one, shipped with `office` (`executor`, `knowledge`, `artifact-share`, `design`, `browser`, `aws-emulator`, `repos`, `skills`), is `{ name, settings }` under `packages:`; the core packages (`office`, `opencode`, `references`, `seeds` and the rest) need no entry; one from another repository is `{ name, repo, path, ref, settings }` (`ref` a tag or full commit SHA). `settings` are as its definition (the file its `package.json` names) declares. Then `office sync` and commit what it writes outside `.office/`, and `.office/seeds/` (the receipts and the bytes of the seed files it laid down): it installs the package in `.office/packages/<name>/`, which stays out of Git, and locks a Git package's commit in `office.lock`, which every machine's sync then installs. The plugin it registers loads everywhere with no `opencode.jsonc` edit and provides what the package gives OpenCode, its skills and MCP servers included, with nothing to enable; files it seeds outside its folder are the office's, created once (a deleted one stays deleted, on every clone: `.office/seeds/receipts.json` keeps a receipt for each); when the package changes one, sync replaces it only while it is unchanged. A package shipped with `office` updates with `office`; a copied one when you change `ref` and sync, or with `track` set, `office packages update` |
| Take a package's change to a file it seeded | Sync reports an edited file whose package changed its seed as pending, and `office check` counts them. `office seeds diff` lists them; `office seeds diff <path>` shows what the package changed and what the office changed, then guidance. Merge into the file, keeping the office's deletions, then `office seeds settle <path>`, and commit the file and `.office/seeds/`. Settling without editing declines the change |
| Remove a package | Delete its entry under `packages:`, then `office sync` and commit what changed outside `.office/`, and `.office/seeds/` (the receipts it dropped). For an official or copied package, sync removes `.office/packages/<name>/`; for a copied package it also removes its `office.lock` entry. Files a package seeded stay, edited or not: sync names each as left in place and drops its receipt; delete the ones you don't want. A package written for this office stays until you delete its folder. A core package can't be removed |
| Keep skills in a folder outside the office out of its sessions | `~/.claude/skills/synced`, where the Claude desktop app syncs account skills, is always left out unless the `office` package's `ignore_claude_synced_skills` setting is `false`. For other folders, add them to its `ignore_skill_folders` setting, `packages: [{ name: office, settings: { ignore_skill_folders: [~/.agents/skills/unwanted] } }]` (absolute, starting with `~`, or relative to the office root; they add to the synced folder), then `office sync`. Every skill in it, at any depth and including ones added later, is removed from the office's sessions with no restart, and skills beside the folder still load |
| Change a package in `.office/packages/` | Don't edit it there: those copies are read-only, `office check` fails on an edit and `office sync` restores the copy. Copy the package into `packages/<another name>/`, list that instead of the original, and sync |
| Write or extend a package for this office | Use `office-package-creator` to build it under `packages/<name>/` and verify it from a fresh session in the office |
| Give a package a desktop app panel | Build its bundle, such as `gui/dist/gui-experimental.cjs`, with the package's own script (the panel reads data over RPC from the package's plugin, through `props.session.server.client.rpc(...)`), and register it in `setup` with `opencode.panels.add(ctx, { file })` from `@office/opencode`. Run `office sync` on the host, not in the container: it installs the panel on the machine the desktop app runs on (Windows from WSL) as plugin `office-<name>`, registers it in that machine's `opencode.json`, and the app reloads it. While building a local package's panel, `office gui dev <name>` installs each new build. `office check` says whether it is installed, registered and this office's build; another office's sync of the same panel replaces it. A removed package's panel stays installed: `office check` says how to delete it. The `opencode-plugin` skill says how to see the panel render |
| Change an Executor app | With the `executor` package selected: edit `executor-apps/<slug>/`, describe it in `package.json`'s `description`, then run `office apps deploy` (`office up` also deploys changed apps). List catalog apps, by catalog ID, under its `settings.catalog_apps`; a package's own app follows that package's settings |
| Turn on a package's system setup (such as the browser package's `system_chrome`), or install `machine.toml`'s `[bootstrap.packages]` | Change `office.yaml` or `machine.toml`, then the user runs `office setup` in their terminal: it lists what the office's own files still need, applies it through mise on their yes (mise asks for sudo), checks, verifies, and offers to restart a managed OpenCode server running with older settings. Never run it, `mise bootstrap` or sudo from a session; `office check` names what is missing and shows a pending restart as a warning |
| Add a file-system job | Add a plain `.sh` script to `cron/` and declare it under the cron package's settings in `office.yaml`: `- { name: cron, settings: { jobs: { job-name: { schedule: '0 6 * * *', script: cron/script.sh } } } }` under `packages:` (a core package need not be listed; list it once to configure it). Times are UTC; scripts run from the office root. Apply the schedule with `office up`. `office cron list` gives the ids for `office cron run <job-id>`. To change a package's job, add `overrides: { package.<package>.<job>: { schedule: '15 9 * * *' } }` or `{ enabled: false }` beside `jobs`. While a selected package fails to load, every scheduled job fails naming it |
| Pin a tool | Exact versions in the root's `mise.toml` for the office's folders, or in `machine.toml` at the root for the whole machine (mise loads it only through its link in mise's global conf.d: a host-mode office makes it once the user agreed in `office setup`, the container at start). Packages' tools are in `machine.packages.toml` at the root: sync owns which tools it lists and each line's comment, so change only versions there (sync raises one below what a package needs); to hold a tool back below a package's version, pin it in `machine.toml`, which wins (`office check` warns). `.office/mise/<package>.toml` is a package's mise setup, sync's alone. SOPS, age, gh and pre-commit come from the `office` package (in `machine.packages.toml`), the versions the office CLI itself runs: don't pin them again elsewhere. The daily `upgrade-tools` job bumps them all and commits as the office's identity, else `office cron`; it skips a file with uncommitted changes |
| Set who the office commits as | `git: { name, email }` in `office.yaml`, then `office up`. It is the container's git default and the cron jobs' identity; a repository's own config overrides it |
| Clone or push a private GitHub repository | Add `credentials: gh` under `git:` in `office.yaml`, then the user runs `office setup` on the host: their browser login with the office's gh, and `gh auth setup-git`. The login belongs to the user: never run `gh auth login`, `logout` or `switch` from a session |
| Let a service in `compose.yaml` call Executor | Add `env_file: [{ path: "${OFFICE_STATE}/office-executor.env", required: false }]` and `EXECUTOR_URL: http://executor:4400` to the service, then `office up`. It gets the office's key as `EXECUTOR_TOKEN` and `EXECUTOR_ORGANIZATION`; never print or copy them |
| Run a command in the container from the host | `office exec -- <command>`, or `office shell`, from the folder it should run in |
| Manage host OpenCode | In `office.yaml`, `opencode.managed: true` opts into the office's systemd user service; otherwise host mode only attaches. `office check` identifies a server outside the unit. Ask before running `office up --upgrade`: it can take over or restart OpenCode, disconnect sessions and close terminals. Keep server credentials in `secrets.server` (SOPS) or obtain them with `opencode.env_commands`; never print either source's values |
| Change a pinned OpenCode, Claude Code, Codex, Executor, mise or sfw version | Edit its version under `tools:` in `office.yaml` (`claude: 2.1.327`, or `version:` in its mapping), run `office pin`, commit `office.yaml` and `office.lock`, then `office up --upgrade`. The daily `upgrade-tools` job bumps them too, once a release is `minimum_release_age` old, or the runtime's own `minimum_release_age` in its mapping; it never restarts anything. Never set an older OpenCode or Executor than the office has run. Managed host OpenCode, Claude Code and standalone Codex use their native updaters at 07:30 UTC. Use `office cron run package.office.update-agent-clis` from a separate terminal to run that update on demand |
| Install a package (npm, pnpm, pip, uv, cargo, mise) | Just run the package manager: in the container, and on a host-mode machine in a shell that sources `~/.local/share/office/env.sh`, it is a wrapper that runs it through Socket Firewall (`sfw`), and mise's installs go through it too. A refusal ends with `=== Socket Firewall ===` and `blocked <ecosystem> package: …; reason: malware`: stop and tell the user; never route around it (a real binary by its path, another registry, an older cache). Package managers and mise take only releases at least `minimum_release_age` old (`3d` unless `office.yaml` says otherwise), so a just-published version isn't found yet; changing the age, and `enabled: false` in sfw's entry under `tools`, which turns the firewall off, are the user's call. A script that runs a mise-managed tool many times runs faster under `mise exec -- <script>`, which keeps the wrappers first |
| Update the container's Debian packages, Chromium among them | `office up --refresh` rebuilds the image with current ones and restarts the container. In container mode a host systemd timer runs it every Sunday; `office check` warns when the last refresh is more than eight days old |

`office check` reports drift between `office.yaml` and the folders, and lists, for information, what sessions load from outside the office, such as skills and plugins in the home folder. `office instructions [folder]` prints the guidance the office plugin gives a session in that folder.
