# Working on the office

Use `office` from any folder inside the office; `office.yaml` declares its structure. For onboarding after init/clone, run `office setup`. Credential display is human-only: let the human run `office executor credentials` in their terminal, keeping passwords out of agent transcripts. Private age identities and runtime state belong outside the repo; commit only public recipients and SOPS-encrypted records.

| To | Do |
|---|---|
| Add a desk | Add it under `desks:` with a description, then `office sync`. Sync scaffolds `<desk>/` with `AGENTS.md`, `.opencode/opencode.jsonc`, `mise.toml` and a starter Executor app (unless the desk sets `app: false`). Deploy the app with `office apps deploy` |
| Clone a repository for a desk | Add `{ name, url, description }` under `desks.<desk>.repos`, then `office sync` |
| Add a reference | Add `{ name, url, ref?, description }` under `references:`, then `office sync` |
| Add a skill | Create `skills/<id>/SKILL.md`, enable it under `skills.enabled` (every desk) or `desks.<desk>.skills` (one desk), then `office sync` to link it |
| Copy a skill from another repository | Add `{ name, repo, ref, path }` under `skills.copied`, enable it, then `office sync`. Commit the copy |
| Add a plugin | A local plugin goes in `.opencode/plugins/<name>/`; the links there are packages' plugins, which `office sync` keeps. A published one is one line in `.opencode/opencode.jsonc` `plugins`. One developed in another repository goes under `plugins:` in `office.yaml` |
| Add a package | A built-in one (`knowledge`, `artifact-share`, `design`, `browser`) is `{ name, settings }` under `packages:`; one from another repository is `{ name, repo, path, ref, settings }` (`ref` a tag or full commit SHA). `settings` are as its `package.yaml` declares. Then `office sync` and commit what it writes: it installs the package in `.office/packages/<name>/`. Its plugin loads everywhere with no `opencode.jsonc` edit and provides what the package gives OpenCode, its skills and MCP servers included, with no `skills.enabled` entry; files it creates outside its folder are the office's, created once (a deleted one stays deleted). A built-in package updates with `office`; a copied one when you change `ref` and sync |
| Remove a package | Delete its entry under `packages:`, then `office sync` and commit. For a built-in or copied package, sync removes `.office/packages/<name>/` and each file it created that is unchanged, keeps and names the changed ones, and leaves the office's own files. A package written for this office stays until you delete its folder. The `office` package can't be removed |
| Change a package in `.office/packages/` | Don't edit it there: those copies are read-only, `office check` fails on an edit and `office sync` restores the copy. Copy the package into `packages/<another name>/`, list that instead of the original, and sync |
| Write a package for this office | `packages/<name>/` (not a built-in package's name) with `package.yaml` (`name`, `description`, `settings`, each with `description` and `default` or `required: true`, `tools`, mise tools at exact starting versions, which `office sync` writes to `.office/mise/<name>.toml`, and `host`, what only a host-mode office gets: more `tools`, an `install` (an executable it creates, or a regular file with `executable: false`), and `path` folders and `env` variables for the office's environment file, plain data only), `skills/<id>/SKILL.md` (loaded only when the package's plugin registers them with `ctx.skill.transform`), `plugin/` (an OpenCode plugin importing only Node's and Bun's built-ins, `@opencode/plugin` and `effect`, finding its package folder with `realpathSync` and the office by walking up to `office.yaml`, and reading its package's `.settings.json` itself), `scripts/`, `template/`, and for a desktop app panel `gui/` (`src/`, `package.json` with its build dependencies, and the built `dist/gui-experimental.cjs`, committed); list it under `packages:` with only its `name` and `settings`, then `office sync`. Load the `opencode-plugin` skill to write and verify its plugin and panel |
| Give a package a desktop app panel | Build its `gui/dist/gui-experimental.cjs` with the package's own script (the panel reads data over RPC from the package's plugin, through `props.session.server.client.rpc(...)`). Run `office sync` on the host, not in the container: it installs the panel on the machine the desktop app runs on (Windows from WSL) as plugin `office-<name>`, registers it in that machine's `opencode.json`, and the app reloads it. While building a local package's panel, `office gui dev <name>` installs each new build. `office check` says whether it is installed, registered and this office's build; another office's sync of the same panel replaces it. A removed package's panel stays installed: `office check` says how to delete it. The `opencode-plugin` skill says how to see the panel render |
| Change an Executor app | Edit `executor-apps/<slug>/` for a shared Executor app or `<desk>/executor-apps/<slug>/` for a desk Executor app. Describe it in `package.json`'s `description`, then run `office apps deploy` |
| Add a file-system job | Add a plain `.sh` script to `cron/` and declare `cron: { job-name: { schedule: '0 6 * * *', script: cron/script.sh } }` in `office.yaml`. Times are UTC; scripts run from the office root. Apply the schedule with `office up`. `office cron list` gives the IDs for `office cron run <job-id>`. To override a package's job, put `cron: { job-name: { schedule: '15 9 * * *', enabled: false } }` beside its `name` and `settings` under `packages:` |
| Pin a tool | Exact versions in the root's or a desk's `mise.toml` for that folder, or in `machine.toml` at the root for the whole machine (mise loads it only through its link in mise's global conf.d: a host-mode office makes it once the user agreed in `office setup`, the container at start). `.office/` is the tool's: a package's `.office/mise/<package>.toml` is sync's list, so change only its versions. SOPS, age, gh and pre-commit come from the `office` package (`.office/mise/office.toml`), the versions the office CLI itself runs: don't pin them again elsewhere. The daily `upgrade-tools` job bumps them all and commits as the office's identity, else `office cron`; it skips a file with uncommitted changes |
| Set who the office commits as | `git: { name, email }` in `office.yaml`, then `office up`. It is the container's git default and the cron jobs' identity; a repository's own config overrides it |
| Clone or push a private GitHub repository | Add `credentials: gh` under `git:` in `office.yaml`, then the user runs `office setup` on the host: their browser login with the office's gh, and `gh auth setup-git`. The login belongs to the user: never run `gh auth login`, `logout` or `switch` from a session |
| Let a service in `compose.yaml` call Executor | Add `env_file: [{ path: "${OFFICE_STATE}/office-executor.env", required: false }]` and `EXECUTOR_URL: http://executor:4400` to the service, then `office up`. It gets the office's key as `EXECUTOR_TOKEN` and `EXECUTOR_ORGANIZATION`; never print or copy them |
| Run a command in the container from the host | `office exec -- <command>`, or `office shell`, from the folder it should run in |
| Manage host OpenCode | In `office.yaml`, `opencode.managed: true` opts into the office's systemd user service; otherwise host mode only attaches. `office check` identifies a server outside the unit. Ask before running `office up --upgrade`: it can take over or restart OpenCode, disconnect sessions and close terminals. Keep server credentials in `secrets.server` (SOPS) or obtain them with `opencode.env_commands`; never print either source's values |
| Change a pinned OpenCode, Claude Code, Codex, Executor, mise or sfw version | Edit `versions:` in `office.yaml`, run `office pin`, commit `office.yaml` and `office.lock`, then `office up --upgrade`. The daily `upgrade-tools` job bumps them too, waiting the ages under `upgrades:`; it never restarts anything. Never set an older OpenCode or Executor than the office has run. Managed host OpenCode, Claude Code and standalone Codex use their native updaters at 07:30 UTC. Use `office cron run package.office.update-agent-clis` from a separate terminal to run that update on demand |
| Install a package (npm, pnpm, pip, uv, cargo, mise) | Just run the package manager: in the container, and on a host-mode machine in a shell that sources `~/.local/share/office/env.sh`, it is a wrapper that runs it through Socket Firewall (`sfw`), and mise's installs go through it too. A refusal ends with `=== Socket Firewall ===` and `blocked <ecosystem> package: …; reason: malware`: stop and tell the user; never route around it (a real binary by its path, another registry, an older cache). Package managers take only releases at least three days old, so a just-published version isn't found yet. A script that runs a mise-managed tool many times runs faster under `mise exec -- <script>`, which keeps the wrappers first. `socket_firewall: false` in `office.yaml` turns the firewall off; that is the user's call |
| Update the container's Debian packages, Chromium among them | `office up --refresh` rebuilds the image with current ones and restarts the container. In container mode a host systemd timer runs it every Sunday; `office check` warns when the last refresh is more than eight days old |

`office check` reports drift between `office.yaml` and the folders. `office instructions [folder]` prints the guidance the office plugin gives a session in that folder.
