# Built-in packages

- A package supplies its own OpenCode plugin. That plugin registers its skills, MCP servers and hooks; the required `office` plugin is not a loader for other packages. Use `office.yaml` for office settings rather than making users configure the same feature again in OpenCode.
- Name the package for the capability the office selects; keep a recognizable tool name for what agents and operators interact with. For example, an office enables `design` but calls the `doop` MCP server and operates `doop` services and volumes. Package state still belongs to `design`.
- Every package has a `package.json`: `name` `@office/<name>`, `description`, `private: true`, `office.definition`, `office.dependencies` naming each `@office/…` package it imports (type-only imports too), except `@office/sdk`, which is always available and never listed, and `exports` for what other packages may import (`{}` when nothing). Reach another package only through an `@office/…` import of an export, never by relative path; the repository's `tsconfig.json` `paths` maps each export for the typecheck.
- A definition is `export default Package.define({...})` from `@office/sdk` (the repository's `sdk/`): settings as one JSON Schema, commands declared under `commands` (each `run` gets `{ office, entries, settings, args }` and parses its own `args`), optional `sync` and `check` functions (a `check` only reports, never writes), `committed` folders under `.office/`, registries made with `Registry.define` (with a `key` when entries must be unique; an entry is any JSON object its parser checks) and registered in `setup` with `ctx.registry`. It states no name or description; those are in `package.json`. Seeded files are declared with `seeds.add` from `@office/seeds` in `setup`, never found by folder name. Core packages (always on: `tooling`, `mise-integration`, `office`, `references`, `seeds`) are listed in `requiredPackages` in `src/packages.ts`; official ones are on when `office.yaml` lists them.
- A package must work as delivered to an office. Scripts have Bun but no dependency install, including in CI. Vendor a needed script library from an exactly pinned devDependency (`artifact-share` is the example). A plugin imports only what OpenCode supplies or ships a bundle. Resolve its own folder through `realpathSync` before opening sibling resources: OpenCode loads the plugin through a link.
- For an artifact-share renderer update, change its root devDependency pin, run `pnpm install`, then `pnpm run vendor-artifact-share` and rebuild a site. The generator also refreshes the skill's diagram references from the matching Pele tag and needs network access.
- A desktop panel is GUI-only on the desktop machine (Windows for a Windows app using WSL). Reach the session server's package plugin over RPC. Verify a panel in the desktop app; a successful server plugin load doesn't show that the panel rendered.
- Use the office's declared mode in `.office.json` to select capabilities. For browser work, agent-browser is for headless automation; Browse is for the user's Chrome in host mode. Keep one relay for that browser. Let Browse update with its extension: pinning just the relay breaks protocol compatibility.
- Package tools must follow the agent outside the office, including into temporary folders. Declare the exact version the package was tested with: an office starts there and sync raises it to a newer declared version, while newer versions are the office's choice. Leave general-purpose platform runtimes to the machine unless the package itself needs one.
