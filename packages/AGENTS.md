# Built-in packages

- A package supplies its own OpenCode plugin and registers its folder in `setup` with `opencode.plugins.add` (a desktop panel with `opencode.panels.add`), both from `@office/opencode`; nothing is found by folder name. That plugin registers its skills, MCP servers and hooks; the required `office` plugin is not a loader for other packages. A folder offered as a standalone skill, which the office enables by ID, is registered with `skills.add` from the optional `@office/skills`; skills a required tool generates, with `skills.sources.generated` and the handle `tools.require` returned in the same `setup`. Use `office.yaml` for office settings rather than making users configure the same feature again in OpenCode.
- Name the package for the capability the office selects; keep a recognizable tool name for what agents and operators interact with. For example, an office enables `design` but calls the `doop` MCP server and operates `doop` services and volumes. Package state still belongs to `design`.
- Every package has a `package.json`: `name` `@office/<name>`, `description`, `private: true`, `office.definition`, optional `office.access` (a pure `Package.access` module importing only `@office/sdk` and its own files, which setup runs before any package set exists), `office.dependencies` naming each `@office/…` package its definition or shared modules import (type-only imports too), except `@office/sdk`, which is always available and never listed, and `exports` for what other packages may import (`{}` when nothing). A package that uses another only when the office selects it maps it in `office.integrations`, not `office.dependencies`, to a module of its own, the only place it imports that provider, whose default export is `Package.integration<typeof definition>()({ setup })`; office runs it whenever the provider is selected, so its `setup` adds only what the package's one settings schema asks for, and the base `setup` rejects an explicit request for an unselected provider with `ctx.providers.selected(name)`; never import an optional provider from the base definition. Reach another package only through an `@office/…` import of an export, never by relative path; the repository's `tsconfig.json` `paths` maps each export for the typecheck.
- A definition is `export default Package.define({...})` from `@office/sdk` (the repository's `sdk/`); its name and description are in `package.json`. See [Packages](../README.md#packages) for definition fields and lifecycle functions. A command parses its own `args`, returns data with `result` (diagnostics go on standard error) or uses the caller's terminal and exit status with `run`, and throws an `Error` for a one-line failure. A `check` only reports, and `down` gets no `entries` and undoes only what its package installed. A command changes its own settings only through `replaceSetting`, one existing scalar at a time. A `sync` names the paths it placed for this machine with `exclude`; a command, an `up`, or a sync about to throw changes its own paths' exclusions at once with `updateExcluded`.
- Register seed files in `setup` with `seeds.add` from `@office/seeds` and jobs with `cron.add` from `@office/cron`. Keep a job's script plain shell, independent of the runner: a missed run must catch up under both systemd and Supercronic. `requiredPackages` in `src/loader/sources/selection.ts` lists the always-on packages; list an official package in `office.yaml` to select it, or a required package once to configure it.
- Keep delivered plugins self-contained: import within the registered directory, use what OpenCode supplies, or bundle dependencies (`bundledPlugins` in `src/tool.ts`). Find the office from the plugin's own folder with `officeRootOf`; built-ins read other assets from `.office/packages/<name>/`. Plugins and Bun scripts read settings through `@office/sdk/applied-settings`; plain Node callers use `office settings get`. Scripts that need a library vendor it from a pinned devDependency (see `artifact-share`).
- For an artifact-share renderer update, change its root devDependency pin, run `pnpm install`, then `pnpm run vendor-artifact-share` and rebuild a site. The generator also refreshes the skill's diagram references from the matching Pele tag and needs network access.
- The `executor` package owns Executor apps: other packages offer one only through `@office/executor/apps` from an adapter, never by deploying it themselves. It type-checks apps against the `apps` version the connected Executor reports, and keeps generated upload bytes (`office.ts`, `package.ts`, the framework pin) stable: a byte change redeploys every office's app.
- A desktop panel is GUI-only on the desktop machine (Windows for a Windows app using WSL). Reach the session server's package plugin over RPC. Verify a panel in the desktop app; a successful server plugin load doesn't show that the panel rendered.
- Use the office's declared mode in `.office.json` to select capabilities. For browser work, agent-browser is for headless automation; Browse is for the user's Chrome in host mode. Keep one relay for that browser. Let Browse update with its extension: pinning just the relay breaks protocol compatibility.
- Package tools must follow the agent outside the office, including into temporary folders. Require a CLI with `tools.require` from `@office/tools`, at the exact version the package was tested with and naming each executable it exposes; that is a floor, while newer versions are the office's choice (`office bump`). Keep a feature's tool inside that feature's setting check, and mark a host-only one `hostOnly`. A script or plugin that runs the tool gets it from `resolveTool(officeRoot, { name, minimum, bin })` of `@office/tools/applied`, with the same name and minimum, never by PATH: only `ready` is an executable it may run, and only `container` falls back to the container's own. Leave general-purpose platform runtimes to the machine unless the package itself needs one.
