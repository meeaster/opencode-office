# Built-in packages

- A package supplies its own OpenCode plugin and registers its folder in `setup` with `opencode.plugins.add` (a desktop panel with `opencode.panels.add`), both from `@office/opencode`; nothing is found by folder name. That plugin registers its skills, MCP servers and hooks; the required `office` plugin is not a loader for other packages. A folder offered as a standalone skill, which the office enables by ID, is registered with `skills.add` from the optional `@office/skills`. Use `office.yaml` for office settings rather than making users configure the same feature again in OpenCode.
- Name the package for the capability the office selects; keep a recognizable tool name for what agents and operators interact with. For example, an office enables `design` but calls the `doop` MCP server and operates `doop` services and volumes. Package state still belongs to `design`.
- Every package has a `package.json`: `name` `@office/<name>`, `description`, `private: true`, `office.definition`, optional `office.access` (a pure `Package.access` module importing only `@office/sdk` and its own files, which setup runs before any package set exists), `office.dependencies` naming each `@office/…` package its definition or shared modules import (type-only imports too), except `@office/sdk`, which is always available and never listed, and `exports` for what other packages may import (`{}` when nothing). A package that uses another only when the office selects it maps it in `office.integrations`, not `office.dependencies`, to a module of its own, the only place it imports that provider, whose default export is `Package.integration<typeof definition>()({ setup })`, and says when it is active in its definition's `integrations` from its one settings schema; never import an optional provider from the base definition. Reach another package only through an `@office/…` import of an export, never by relative path; the repository's `tsconfig.json` `paths` maps each export for the typecheck.
- A definition is `export default Package.define({...})` from `@office/sdk` (the repository's `sdk/`): settings as one JSON Schema, commands declared under `commands`, each with exactly one handler getting `{ office, entries, settings, args }` and parsing its own `args`: `result` returns the text that is all of its standard output (data a caller reads; diagnostics, Clack included, go to standard error), `run` acts with the caller's terminal and exit status, optional `sync`, `fullSync`, `session`, `check`, `up` and `down` functions (`fullSync` items run only at a full sync after its own admission and application; a `check` only reports, never writes; `down` gets no `entries` and must undo only what its package installed; `check`, `up` and `down` reach the package's own systemd timers through `host.timers`), `committed` folders under `.office/`, registries made with `Registry.define` (with a `key` when entries must be unique; an entry is any JSON object its parser checks) and registered in `setup` with `ctx.registry`. It states no name or description; those are in `package.json`. Seeded files are declared with `seeds.add` from `@office/seeds` in `setup`, never found by folder name, and scheduled jobs with `cron.add` from `@office/cron`. A command changes its own settings only through `replaceSetting`, one existing scalar at a time; a `sync` names the paths it placed for this machine with `exclude`, which keeps them out of commits, and a command, or a sync about to throw, changes its own paths' exclusions at once with `updateExcluded`. Keep a job's script plain shell, independent of the runner: it runs from a host timer or from Supercronic in the container, and a missed run must catch up in either mode. Core packages (always on: `tooling`, `mise-integration`, `opencode`, `office`, `references`, `seeds`, `cron`; one need not be listed in `office.yaml`, which lists it once to configure it) are listed in `requiredPackages` in `src/packages.ts`; official ones are on when `office.yaml` lists them.
- A package must work as delivered to an office. Scripts have Bun but no dependency install, including in CI. Vendor a needed script library from an exactly pinned devDependency (`artifact-share` is the example). A plugin imports only what OpenCode supplies or ships a bundle; a built-in one ships it by being listed in `bundledPlugins` (`src/tool.ts`). Plugins and scripts read their settings from the office's applied settings through `@office/sdk/applied-settings`, which a Bun script resolves from the package set sync installed (plain Node can't run its TypeScript there; use `office settings get`). Resolve its own folder through `realpathSync` before opening sibling resources: OpenCode loads the plugin through a link.
- For an artifact-share renderer update, change its root devDependency pin, run `pnpm install`, then `pnpm run vendor-artifact-share` and rebuild a site. The generator also refreshes the skill's diagram references from the matching Pele tag and needs network access.
- A desktop panel is GUI-only on the desktop machine (Windows for a Windows app using WSL). Reach the session server's package plugin over RPC. Verify a panel in the desktop app; a successful server plugin load doesn't show that the panel rendered.
- Use the office's declared mode in `.office.json` to select capabilities. For browser work, agent-browser is for headless automation; Browse is for the user's Chrome in host mode. Keep one relay for that browser. Let Browse update with its extension: pinning just the relay breaks protocol compatibility.
- Package tools must follow the agent outside the office, including into temporary folders. Declare the exact version the package was tested with: an office starts there and sync raises it to a newer declared version, while newer versions are the office's choice. Leave general-purpose platform runtimes to the machine unless the package itself needs one.
