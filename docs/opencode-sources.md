# Which OpenCode config and plugins reach a desk?

`office opencode inspect [folder]` shows what is declared or present **on disk** for a location. Run it in the office, pass a folder from elsewhere, or use `--office /path/to/office` (a relative folder then starts there). Omit the folder to inspect the current directory, or the explicit `--office` directory. It works before OpenCode starts, including in container mode.

```text
office.yaml                                  # packages: [{name: common}]
packages/common/office.ts                    # Office package definition
packages/common/plugin/index.js              # OpenCode server plugin
.opencode/plugins/common                     # sync's relative link to ../../packages/common/plugin
.opencode/plugins/imported                   # sync's link to ../../.office/plugins/imported, a plugins: clone
.opencode/plugins/mine/                      # the owner's own plugin, committed; sync never touches it
.opencode/opencode.jsonc                     # owner config shared by both desks
builder/.opencode/opencode.jsonc              # owner config for builder and its descendants
builder/extensions/local/index.js             # explicitly configured by builder
builder/.opencode/plugins/independent.js      # discovered by OpenCode in builder
builder/repos/sample/opencode.json            # owner config at a nested repo
sibling/                                     # inherits common, not builder's sources
```

For example, in `builder/.opencode/opencode.jsonc`:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  // Relative to this file, not to the CLI's current directory.
  "plugins": [{ "package": "../extensions/local" }],
  "commands": { "scope-setting": { "description": "builder-override", "template": "Builder" } },
}
```

`builder/extensions/local/index.js` can use the ordinary [OpenCode plugin API](https://opencode.ai/docs/build/plugins/server):

```js
export default {
  id: "builder-command",
  async setup(ctx) {
    await ctx.command.transform(editor => editor.add({
      name: "builder-command", description: "A command for builder",
      async execute() { /* your command here */ },
    }));
  },
};
```

Output excerpt from `office opencode inspect builder/repos/sample`:

```text
OpenCode sources for builder/<folder-2>/<folder-3> (office-relative; runtime not checked)
Ordinary project discovery inside the office only; external config, policies and runtime overrides are not evaluated.
[folder builder/<folder-2>/<folder-3>] native config: builder/<folder-2>/<folder-3>/opencode.json
[office] native config: .opencode/opencode.jsonc
[desk builder] native config: builder/.opencode/opencode.jsonc
[desk builder] configured local directory: builder/.opencode/opencode.jsonc#plugins[0]
[office] Office package link (selected local package): .opencode/plugins/common
[desk builder] convention plugin candidate: builder/.opencode/plugins/<entry-1>
```

## Who owns each source?

- **Native:** Edit models, permissions, MCP, commands and plugin entries in your own `opencode.json(c)`. Ordinary [V2 project discovery](https://opencode.ai/docs/config) applies direct files from farthest to nearest, then `.opencode` files from farthest to nearest (`.json` before `.jsonc`). A desk `.opencode` document can therefore override a **nested repo's direct** document. A Git boundary does not stop the search. Only ancestors of the chosen folder participate. For one desk, use its native config or its `.opencode/{plugin,plugins}/` immediate directories or `.js`/`.ts` files. A `plugins/` directory next to a direct config is not auto-discovered, and a configured local path must be a directory. Project settings need no Office sync.
- **Office package:** `office sync --packages` applies selected packages, including a root link for each installed `plugin/`. Package `.settings.json` and `.office.json` keep their existing readers. There is no desk package selector. Desk code or an explicit native desk entry is the way to narrow scope; selecting a package and referencing its linked plugin again in a desk does not make the root link desk-only.
- **Which entries are Office's:** An entry of `.opencode/plugins/` or `.opencode/skills/` is Office's exactly when it is a symlink whose target text is one Office writes there; nothing records which links Office made. At the root those are `../../.office/packages/<name>/<path>` and `../../packages/<name>/<path>` (a package's server plugin, `plugin` by convention or the directory its `opencode(ctx)` registers), `../../.office/plugins/<name>` (a Git clone), `../../skills/<name>` (a library skill) and `../../packages/<package>/skills/<name>` or `../../.office/packages/<package>/skills/<name>` (package skill links earlier releases made). In a desk's `.opencode/skills/` they are the same skill paths one level deeper (`../../../skills/<name>`). `<name>` is always the entry's own name. Office delivers plugins only at the root, so a desk's `.opencode/plugins/` is entirely the owner's. Real folders, files and links to anything else are the owner's: Office never changes or removes them, and when one has the name Office wants, sync refuses and reports it instead. The rule is deliberately broad: any `../../packages/<name>/<path>` or `../../.office/packages/<name>/<path>` plugin link whose entry name equals the package name counts as Office's, whatever the asset path and whether or not that package is selected, and so do the old package-skill link forms. It can't be narrowed without a ledger: once a package is deselected or its registration changes its server directory, nothing on disk says which path Office linked, so recognizing and withdrawing that link needs the whole shape. Because the rule is the text, a deselected package's link, a dangling link and a link the owner made by hand with exactly Office's text are all Office's: sync removes them when nothing selects them, and recreates them if the package is selected again. A still-selected but unreadable package keeps its link. Sync refuses a redirected desk folder, `.opencode`, plugin or skill folder, or `.office/plugins/`. Development builds before this rule kept link receipts in `.office/resolved/opencode-links.sqlite`; sync deletes that file. Full sync retains the existing migrations for recognizable legacy **bundles** and the exact historical Executor MCP entry; it does not generate or merge native config.
- **A plugin's location is fixed while OpenCode runs:** a running server keeps loading a plugin from the directory it first resolved for that name; if the link then leads elsewhere, the plugin silently stops loading until the server restarts. Sync updates clones in place and keeps each link's text, so ordinary syncs need no restart. When a name must point elsewhere (a package moved between `.office/packages/` and `packages/`, a registered server directory changed, or a name passed between a package and a clone), sync makes the change and prints `restart OpenCode to pick up <name>`; `office check` reports such a link before sync relinks it. Against a running server, check expects each package plugin and each linked clone, and when one isn't loaded it suggests restarting OpenCode.
- **Keeping plumbing out of Git:** sync writes one block to the repository's `info/exclude` (from `git rev-parse --git-path info/exclude`, so a worktree office uses the file its worktrees share). The block, between `# office sync: …` and `# end of office sync`, lists `/.office/` (packages, clones, staging and generated state) and each Office link with its full office-relative path, a leading slash and no trailing slash (a trailing slash would not match a link). Sync rewrites only the block, once per run and idempotently, drops lines for entries it withdrew, and replaces the per-clone lines earlier releases wrote outside it: `/.office-plugin-*/` and `/.opencode/plugins/<name>/` for a name `plugins:` declares; a line of that shape for any other name is yours and stays. Markers are recognized with LF or CRLF endings, and the file keeps its line endings. If the markers don't form exactly one block (a start without an end, an end without a start, or duplicates), sync leaves the file unchanged and fails with a message: delete the stray marker lines, or the whole block, and sync again. The file is replaced whole by a rename, from a read made just before, so Git or another sync never reads it half-written. When two syncs (say, cron's and yours) write at once, each keeps every owner line it read and the last rename wins; only an edit you make to the file within that moment can be overwritten. Your `.gitignore` and your own exclude lines are never edited. An office that isn't a Git repository's root gets nothing. Excludes don't affect tracked paths: an office whose earlier release committed `.office/` or Office links keeps tracking them until you untrack them, and `office check` warns with the exact `git rm -r --cached` command (the files stay on disk). Sync never untracks anything itself.
- **Git plugin clones:** `office.yaml`'s `plugins:` selects separate office-wide clones. Each is checked out in `.office/plugins/<name>` and linked as `.opencode/plugins/<name>` -> `../../.office/plugins/<name>` only after the checkout is published (OpenCode doesn't notice a checkout appearing behind an existing link, so a link that was already there is made again). Links are made in `.office/tmp/` and renamed into place without replacement, never as a dot-name in `.opencode/plugins/`, which OpenCode would load as a plugin; where the filesystem can't rename without replacing, the link is created in place, which also never replaces anything. Full sync handles clones; `sync --packages` skips their fetch and keeps their links. Updates fetch and check out inside the existing checkout; a new clone is never renamed over one. Withdrawing a `plugins:` entry removes its link and keeps its checkout, which may hold local work. An existing checkout is linked before it is fetched, so a fetch that fails (offline, or an auth problem) never leaves it unlinked: a checkout whose link was deleted is linked again if sync can verify it. `office check` lists any `.office/plugins/<name>` that no `plugins:` entry declares, with the path to remove if you don't want it; sync never deletes one. If a withdrawn name is selected again with another repository, sync refuses the old checkout and names the folder to move aside. An earlier release's checkout in `.opencode/plugins/<name>` moves to `.office/plugins/<name>` (moved first, then linked at once, before any fetch, which a running server tolerates) when sync can verify it as this plugin's (worktree and Git directory, declared origin and effective fetch URL, and a commit); otherwise it stays and sync says so. Inspect reports the declaration, whether `.git` is present and whether the link is in place, without running Git. The installer refuses to clear a symlink to make room for a checkout. Before refreshing an existing plugin checkout it checks the worktree, Git directory, declared origin and effective fetch URL; redirected/mismatched checkouts remain untouched. It also refuses a checkout whose HEAD names no commit (such as an empty `git init`), reading HEAD without lazy fetching and without changing its files or `.git`: move it aside so sync can clone afresh. This does not change the refresh rules for desk repos or references.
- **First plugin delivery:** Sync clones only into a destination that does not exist. Anything already there, even an empty folder, is the owner's: sync refuses it and asks you to move it aside. On Linux (glibc `renameat2` with `RENAME_NOREPLACE`) and macOS (`renamex_np` with `RENAME_EXCL`), sync initializes a claim (a folder holding `.git` with the declared origin and a file holding a random token) in a private `.office/tmp/plugin-*` staging folder, on the same filesystem as `.office/plugins/`, then renames it into place without replacement, so Git never writes into a folder that was already there. Git fetches into the claim's `.git`, so path-specific `includeIf` config and the effective-origin check apply at the real destination, and checks out into the staging folder. To publish, sync moves the whole claim back into staging in one rename and keeps it only if it is the same folder (device and inode), holds nothing but `.git`, and that `.git` is the same folder and still holds the token; then it renames the complete checkout into place, again without replacement. Device and inode alone are not identity: a freed inode number is reused by the next entry created (ext4 does so at once), so an owner who deletes the claim and creates a folder, `git init`s or clones there can match them, but cannot hold the token. Until publication OpenCode can see at most the empty claim holding `.git`. A folder or file that replaces the claim, enters it or takes the destination meanwhile is never deleted or replaced: if it was briefly moved into staging for the check, it is renamed straight back with the same inode and metadata (an entry that cannot be checked, such as a file, counts as not Office's), and if that fails, sync names where it is kept and leaves that staging folder, removing from it only Office's own `.git`, identified by the token. Cleanup after a failure removes the claim, or only its `.git`, by the same check. Sync removes only the parts of staging it created itself; it never deletes a staging folder that may hold an entry someone else made. The guarantee covers what appears at the destination; something written inside Office's staging folder while sync runs is not covered. Staging is under `.office/`, which sync keeps out of commits. Elsewhere, or on a filesystem that cannot rename without replacing, the first clone fails and publishes nothing. Updating an existing checkout still checks out in place.

  **Recovering an interrupted first clone.** If the first sync of a plugin is killed (for example during the fetch), the destination keeps the claim, a folder holding only `.git`, and `.office/tmp/` keeps a `plugin-*` folder. No link is made, so OpenCode doesn't see it. The next sync refuses the claim with “existing plugin checkout has no commit”: Office cannot prove the folder is its own, so it doesn't delete it. Check that `.office/plugins/<name>` holds nothing but `.git` and that the `plugin-*` folder holds nothing you want, delete both, then run `office sync` again. A staging folder that sync names in a “kept at” message holds someone else's entry: move that entry back yourself before deleting the folder.
- **Desktop:** A bundle copy and a registration in the app machine's global `plugins` list are separate from the server link. Inspect looks for matching Office panel records on the local app machine and checks only their bundle presence and registration. It neither imports a bundle nor enumerates unrelated global plugins. If Windows discovery would require launching a process from WSL, or the CLI is inside the container, that machine is not inspected. For isolated fixtures, set **both** `OFFICE_APP_CONFIG_DIR` and `OFFICE_APP_PANELS_DIR`. Even a listed bundle may not be rendered.

## Reading the report

Inspect enumerates **office-local candidates**, not OpenCode's effective configuration. It does not evaluate schemas, substitutions, package definitions, plugin entrypoints/IDs, policy, disable/re-enable rules, or version resolution. It excludes global/system config, ancestor config above the office, explicit/inline service config and any differences on a remote machine. External config symlink targets are not read as project config. Filesystem matches use host paths; another server's namespace is not mapped.

The report uses structural names (declared Office package, clone, desk and repo IDs), the config file, and the field and **zero-based array index**. Arbitrary native plugin specs are never echoed, even if they look like safe npm names, hostnames or local paths. `<folder-N>` is the undeclared ancestor at depth N from the office root. `<entry-N>` is the one-based position among candidates in the desk's or root's sorted `plugin/` then `plugins/` scan. Desktop registration checks the name **and path** in a regular panel receipt file and a regular bundle; output omits machine-specific paths. An office can use pinned Git, built-in and local packages without exposing repo URLs or ref values.

For a configured local directory and a convention link resolving to it, the report repeats **both origins** under `same filesystem target`. Recognized npm names that might denote different revisions get a separate `same package name or ID; versions not resolved` note. Neither verifies activation. The CLI cannot detect equal plugin IDs implemented by unrelated source directories.

### Upgrading an existing office

Links earlier releases made already have Office's text, so they are Office's: nothing needs recreating. A package link whose package moved between `.office/packages/` and `packages/` is relinked with a restart notice. Clones move from `.opencode/plugins/<name>` to `.office/plugins/<name>` as described above. The first sync writes the `info/exclude` block. Then follow `office check`'s warning to untrack plumbing the office committed, review the result with `git status`, and commit; the files stay on disk. Release CLIs that wrote per-clone exclude lines rewrite them on their next sync if one runs again, and this CLI moves them back into its block, so upgrade every CLI that syncs the office together.

The old CLI allowed packages to register `opencode inspect`, including aliases and descendants. When the saved generation contains such a claim, the new CLI refuses inspection instead of shadowing or importing the author. Rename the route/alias in the package, or deselect its owner, then run `office sync --packages`. A renewed collision rejects publication; **keep the existing generation**, which remains readable by unrelated commands and retains the commit used for immutable pinned repair.

The compiled `standard/opencode/` owner also accepts [typed registrations from a package's `opencode(ctx)` callback](opencode-authoring.md). Inspect reports the last collected choices separately from current filesystem and app-machine evidence. The callback is not executed by inspect.

### Reproduce the native check

From the CLI checkout on Linux with a clean temporary-file hierarchy and no system OpenCode config:

```sh
OFFICE_TEST_OPENCODE="$(command -v opencode)" \
OFFICE_TEST_PRE_INSPECT=/path/to/compiled-ee0bbc2/office \
bun test ./src/opencode-scope.cli.test.ts
```

The tests compile the production CLI, create their own homes, offices, app and machine paths, and use a local request trap for inspect. The optional old binary publishes real pre-inspect generations, exercises the author commands, then upgrades with a moved tag and missing package copy. The independent native case starts only the supplied V2 binary on an ephemeral loopback port, with its own password, no inherited account environment and model fetching disabled. It reads `/api/command` at the root, both desks, a nested Git repo, and a fresh location after withdrawal. It also declares a Git-cloned plugin and checks that its command, loaded through the link into `.office/plugins/`, is listed at the root, both desks and the nested repo. Without either variable the offline ownership, exclude, inventory and checkout tests still run.
