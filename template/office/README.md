# __OFFICE__ office

An office is a source-controlled folder of work for OpenCode and Claude Code: its instructions, skills, packages and working repositories. It is run with the `office` command; `office --help` lists its commands.

After init or clone, run `office setup` to resume onboarding. It guides host prerequisites, SOPS/age enrollment and owner email, offers to install the system packages and files the office declares (a package's system setup, `machine.toml`'s `[bootstrap.packages]`) through mise when something is missing, creates Executor's owner/token without browser copying, starts OpenCode (offering a restart when a running managed server has older settings), deploys apps and checks. Rerun it after turning on a package's system setup. Review the jobs `office cron list` shows first (the cron package's settings in `office.yaml` add and change them): missed jobs run at container startup. Provider sign-in remains human-controlled; use `office pair` for the app.

In a terminal, `office setup`, `office sync` and `office up` show each stage with a spinner and the last lines of a slow command, and ask their questions as prompts. Without one (an agent, cron, a pipe) they print one plain line per event, `<stage>: <message>`, show a command's output only when it fails (every line with `--verbose`), never prompt, and end with `next:` lines or a stop on stderr. Ctrl+C exits 130; rerun to continue.

Setup asks before installing host mise (newest stable release at least three days old, in `$XDG_DATA_HOME/office/host-tools`, defaulting to `~/.local/share/office/host-tools`) and the tools the office CLI runs, SOPS, age, gh and pre-commit, at the versions `machine.packages.toml` pins (the `office` package's tools; `office upgrade-tools` bumps them). Declining keeps working installed tools. Office finds them without shell activation, global mise selection changes or shell profile edits. For unattended setup, `--install-deps` authorizes these changes; otherwise missing tools stop setup without a prompt. Docker with its daemon and Git remain separately installed prerequisites. Identity creation still requires `--generate-age-key` or interactive consent, and a new owner still needs `--owner-email <email>` or interactive input.

`office.yaml`'s `git` block declares who the office commits as (`name`, `email`) and whether it uses your GitHub login through gh (`credentials: gh`); setup reads it and, when interactive, offers to fill it in (the identity from your global git identity, the key when a source doesn't read without a login). With `credentials: gh`, setup sets GitHub up without further options: gh on the host (one of the office package's tools), one browser login made with `gh auth login` on the host (unattended, setup stops with that command), gh as git's HTTPS credential helper (`gh auth setup-git`, which writes your global git config); `office up` shares the host's gh configuration read-only with the container. Without it there is no GitHub step. Before cloning, setup reads every source and names any that doesn't read, with the likely cause. In container mode the login must be in gh's `hosts.yml` (not the system keyring) and not an expiring token; setup says when it isn't.

`office shell` opens a shell in the running container, in the folder matching the one you are in; `office exec -- <command>` runs one command there. Neither starts anything.

Portable owner credentials are SOPS-encrypted in `secrets/executor-owner.enc.json`, selected by `secrets.executor_owner` in `office.yaml`. Commit encrypted records and public `.sops.yaml` recipients yourself; keep age private identities and runtime state outside this repository. `office executor credentials` deliberately reveals the stored owner login, even offline; `--password-only` is suitable for a clipboard pipe. Never put its output in logs or agent transcripts.

## Layout

| Path | Holds |
|---|---|
| `office.yaml` | Under `tools`: the versions the containers run (and Socket Firewall's, and whether package downloads go through it), and how old a release must be before package managers, mise or the daily job take it. Also the references, cloned plugins and packages, such as the `repos` package's working repositories and the `skills` package's sources and enabled skills |
| `office.lock` | The checksum of each version in `office.yaml`, written by `office pin`, and the commit of each package from a Git repository, written by `office sync`; don't edit it |
| `.office/seeds/` | The `seeds` package's: `receipts.json`, a receipt for each file a package laid down in the office or found already there (a seed), and the bytes of each seed a receipt names, by its SHA-256. Written by `office sync` and `office seeds settle`; a stored seed is never deleted. Committed |
| `AGENTS.md`, `.opencode/opencode.jsonc` | Your instructions and config for every session. No tool writes to `AGENTS.md` |
| `.agents/skills/` | Skills every session loads: your own folders, committed, and, with the `skills` package, its links to the skills it enables, which it records in `.office/skills/links.json` and keeps out of Git. A folder of your own skills such as `skills/` reaches it only as a `skills` package source |
| `.opencode/plugins/` | OpenCode plugins every session loads: your own, committed, and `office sync`'s links to each package's plugin and each `plugins:` clone, which it keeps out of Git |
| `.office/packages/` | Packages pulled into the office, rebuilt by `office sync` and kept out of Git: ones shipped inside the `office` executable, such as the core `office` package (the guidance for a session's folder, which `office instructions` prints, the `office` skill and the `office-executor` MCP server) and `knowledge` (lists the articles in `knowledge/` in every session), and ones copied from another repository. They are read-only: `office check` reports an edit and `office sync` restores the copy. To change one, copy it into `packages/` under a name of your own |
| `.office/mise/` | Packages' mise setup (a host install, a system setup), one file per package, written by `office sync`; don't edit them. `.office/` is the tool's and, but for the folders packages commit such as `.office/seeds/`, stays out of Git (sync excludes it, and its links, in `.git/info/exclude`): what you edit is at the root |
| `packages/` | Packages written in this office |
| `knowledge/` | Articles every session sees listed, through the `knowledge` package |
| `mise.toml` | Tools every folder of the office gets; a working repository's own `mise.toml` adds more |
| `machine.packages.toml` | The mise tools the office's packages need, one line per tool naming the packages, written by `office sync` and committed. Sync owns which tools are listed and raises a version below what a package needs; the versions are otherwise yours, and `office upgrade-tools` bumps them. To hold one back, pin it in `machine.toml` |
| `machine.toml` | Machine-wide tools and mise settings, and system packages under `[bootstrap.packages]` that `office setup` offers to install, the office's own. mise loads it only through a link in its global conf.d, after `machine.packages.toml` and `.office/mise/`, so it wins over them: in host mode sync makes the links once you agree in `office setup`, and the container makes them inside itself. Inside a folder with a `mise.toml`, that file wins |
| `executor-apps/` | Source for the office's Executor apps, one folder per app named by its slug, such as `opencode` (start a session and wait for it). The `executor` package deploys them (`office up`, `office apps deploy`) and lists each in every session with its `package.json` description |
| `office cron list` | Lists the ids of the jobs packages and the office declare that apply in this mode. The required `office` package updates references and tool pins daily. Add the office's own jobs, or reschedule or disable a package's, in the `cron` package's settings: `- { name: cron, settings: { jobs: {...}, overrides: { package.office.upgrade-tools: { enabled: false } } } }` under `packages:`. A core package need not be listed; list it once to configure it. |
| `references/` | Read-only clones, gitignored |
| `repos/` | Working repositories, gitignored: with the `repos` package, the checkouts its settings declare, which every session is told about. A checkout's own `AGENTS.md` applies in sessions started inside it |
| `scratch/` | Throwaway work and Git worktrees, gitignored |
| `Dockerfile`, `compose.yaml` | Optional: system packages on top of the base image, and extra services `office up` starts. A service reaches Executor with the office's key: `env_file: [{ path: "${OFFICE_STATE}/office-executor.env", required: false }]` gives it `EXECUTOR_TOKEN` and `EXECUTOR_ORGANIZATION`, and Executor is at `http://executor:4400` |
| `.pre-commit-config.yaml` | The gitleaks hook, which blocks commits that contain secrets |

## Conventions

- `office init` and `office setup` install git's pre-commit hook in this clone (`pre-commit install`, with the pre-commit the office package provides in `machine.packages.toml`), so commits run the gitleaks hook; they leave a hook of your own alone, and `office check` says the hook's state. In another clone, run `pre-commit install` there before your first commit. The container has the same pre-commit, so commits made there run the hook too.
- OpenCode, Claude Code, Codex, Executor and mise run at the versions under `tools` in `office.yaml`. The daily `upgrade-tools` job bumps them once a release is `minimum_release_age` old (or the runtime's own age) and commits as the office's git identity (else `office cron`); nothing restarts until you run `office up --upgrade`, which backs up and applies them (`office up` alone keeps the applied versions and says what is pending). After changing a version by hand, run `office pin`. An office never goes back to an older OpenCode or Executor.
- `office pair` prints a one-time link that connects the OpenCode app or a browser to this office.

- Change `office.yaml`, then run `office sync`. It clones and fetches, installs, updates, restores and removes packages and applies them, such as the `skills` package's links and the package plugins; it never overwrites hand-written content.
- An Executor app's jobs are its code: a schedule or webhook starts a workflow, which can run an OpenCode session in the office (the `opencode` app). `executor.notifications` in `office.yaml` names the app whose `notifications.send` gets the office's own job notifications.
- Skills at the root (`.agents/skills/`) reach every session in the office, inside working repositories too.
- `office check` reports drift between `office.yaml` and the folders, and the running containers' state.
- OpenCode runs in the office's container or, with `opencode: { mode: host, url: ... }` in `office.yaml`, on a server already running on the host. Executor always runs in a container. After switching, run `office up`, which redeploys the Executor apps for the new mode.
